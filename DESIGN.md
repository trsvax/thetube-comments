# Comment System Design

How comments work on theTube. This is the design.

---

## The protocol

```
POST /w/comment/add?page={pageUuid}&body={body}&author={author}&token={token}&id={idempotencyKey}
```

- `?` present → CloudFront Function logs it, returns 202. Data captured in access log.
- No `?` → Lambda@Edge processes immediately (other namespaces like admin; comments don't use this).

The client contract: POST, check the status code. 2xx = success. 4xx = your fault. 503 = retry later.

---

## Write path

1. Client calls `POST /w/comment/open?page={uuid}` → gets token
2. Client POSTs to `/w/comment/add?page={uuid}&body=...&token=...&id=...`
3. CloudFront Function validates shape (token present, URL not too long, required params exist)
4. Returns 202. Done. The data is in the log.
5. Processor (Lambda, triggered by log delivery) reads log entries, validates, writes files.

The edge is a dumb bouncer. The processor is the gatekeeper.

---

## File layout

```
/comments/{pageUuid}/{requestId}.json   ← individual comment (immutable)
/comments/{pageUuid}/index.json         ← all comments rolled up (regenerated)
```

Filenames are CloudFront request IDs — server-generated, unique, untouchable by the client. Each comment file is immutable once written. The processor writes them freely with no coordination (no sequential numbering, no counter).

`index.json` is the read view — regenerated by the processor after each batch. The client fetches one file, gets all comments.

---

## The processor

One Lambda per namespace. Lives in this repo. Triggered by CloudFront log delivery to S3.

The processor:
1. Reads log entries for `/w/comment/*`
2. Validates: token signature, token expiry, pageUuid exists, body size, shape
3. Deduplicates (by client-generated idempotency key)
4. Writes `/comments/{pageUuid}/{requestId}.json` (using `If-None-Match: *` — create-only)
5. Regenerates `/comments/{pageUuid}/index.json`

No sequential numbering. No counter. No concurrency constraint. Multiple processor instances can run in parallel — each writes to a unique filename (request ID). Scale for free.

### What the processor checks

| Check | Rejects |
|---|---|
| Token signature valid | Forged tokens |
| Token not expired | Stale tokens |
| pageUuid matches a real page | Writes to nonexistent comment spaces |
| Body under size limit | Oversized payloads |
| Idempotency key not seen before | Duplicate submissions |
| Trust level | Routes to moderation or direct write |

---

## index.json (read path)

The client fetches `/comments/{pageUuid}/index.json`. What's behind that URL is pluggable:

**MVP (what we build first):** Static file on S3, regenerated by the processor after each batch. Simple. One Lambda does everything.

**Future upgrade:** Lambda@Edge on the read path. Reads the existing `index.json` + lists any new files since last build, merges, returns fresh result. Same URL, same client code. Swap the implementation behind CloudFront.

**If Lambda is down:** CloudFront serves the stale cached `index.json`. Degrades gracefully — comments are slightly behind, not missing.

The client doesn't know or care what generates the response. It's a namespace. The implementation is internal.

## Trust levels

The client always calls `open` before writing. The trust level is determined by what `open` returns — which depends on the backend implementation at that time.

| Level | `open` returns | What it proves | Processor behavior |
|---|---|---|---|
| Low | Static JWT (CloudFront Function) | Client called open | Moderated (held for review) |
| Medium | Scoped token (Lambda, checks user cookie) | Client is logged in | Auto-filtered, written faster |
| High | Per-request token (Lambda, validates session) | Client asked permission now | Written immediately |
| Admin | Admin token (Lambda, passkey challenge) | Verified admin identity | Full access, sync response |

The client code never changes. It always calls `POST /w/comment/open?page={uuid}`, gets a token, includes it in the write. What happens behind `open` evolves:

- **MVP**: CloudFront Function returns a static JWT. Everyone gets low trust.
- **Add user auth**: Lambda checks for user cookie, returns medium/high trust if present, low trust if not.
- **Add admin**: Lambda checks for admin cookie + passkey, returns admin token.

Each upgrade makes `open` smarter. The client is the same from day one. The processor reads the trust level from the token and acts accordingly.

Trust can also be earned by behavior — comment history, account age, reputation. The `open` Lambda can factor in any signal. The client doesn't know or care why it got the trust level it got. It just uses the token.

### `open` — the platform primitive

```
POST /w/comment/open?page={pageUuid}
→ 200 {"token": "...", "trust": "low|medium|high"}
```

`open` is a verb in the namespace: `/w/{namespace}/open`. One Lambda (or CloudFront Function) handles all namespaces. The namespace is read from the path. The params are namespace-specific — `open` doesn't validate them, it just signs whatever's there into the token. The processor validates the params later.

```
POST /w/comment/open?page={uuid}  → token: {ns:"comment", page:"{uuid}", trust:"low", exp:...}
POST /w/admin/open                → token: {ns:"admin", trust:"admin", exp:...}
POST /w/contact/open?form={id}    → token: {ns:"contact", form:"{id}", trust:"low", exp:...}
```

`open` is privilege escalation. Everyone starts with nothing. Call `open`, get whatever trust level the system decides you deserve:

- Anonymous, no cookies → low-trust token (static JWT, returned by CloudFront Function)
- Logged-in user cookie → high-trust token (Lambda checks the cookie, mints scoped token)
- Admin passkey → admin token (Lambda validates passkey challenge)

MVP: the CloudFront Function returns a static JWT — `HMAC(secret, namespace + params + buildTimestamp)`. Rotates every deploy. TTL of 48 hours. No Lambda needed.

Later: Lambda does real work behind the same endpoint. Checks cookies, validates sessions, computes reputation. Client doesn't change.

The edge can reject `open` based on namespace policy:
- `/w/comment/open` → anyone gets a token (anonymous comments allowed)
- `/w/admin/open` → no admin cookie? 403. Never issues a token.

Per-site policy: some sites return 403 on `open` if not logged in. The platform is the same. The policy is per-deployment.

Every namespace gets `open` for free (platform default). Override with a custom Lambda when you need logic that can't be expressed as config.

## The `?` as security boundary

| Path | Data location | Token location | Logged |
|---|---|---|---|
| `?` present | Query string | Query string | Yes — full URL in access log |
| No `?` | Request body | Auth header/body | URL only — body/headers not in log |

Comments always use `?` → tokens are in the log (disposable, low/medium trust).
Admin uses no `?` → credentials stay off disk (high trust, never logged).

---

## Edge validation (CloudFront Function)

The edge can't do crypto (1ms limit, no libraries). But it can reject obvious garbage:

- No `token` param → 403
- URL too long → 413
- Required params missing → 400
- Known bot patterns (`.php`, `wp-admin`, `..`) → 403
- Everything else → 202

Shape validation at the edge. Real validation in the processor. Bot noise never reaches the logs.

---

## Filename and identity

The client provides: `page` (pageUuid), `body`, `author`, `token`, `id` (idempotency key).

The server controls: the filename. The CloudFront request ID becomes the filename — server-generated, globally unique, untouchable by the client.

Comment file content:

```json
{
  "requestId": "K1jaBcDeFg",
  "body": "hello",
  "author": "someone",
  "date": "2026-05-22T14:30:00Z"
}
```

## IAM isolation

```
Comment Lambda IAM: s3:PutObject, s3:GetObject, s3:ListBucket on s3://bucket/comments/*
```

- Can't read posts, user data, site build, other namespaces
- Can't touch logs (logs are the source of truth, immutable)
- Uses `If-None-Match: *` on individual comment PUTs — create-only, can't overwrite

If the processor is compromised: nuke `/comments/`, fix it, replay the logs. Full recovery.

---

## Rate limiting

Platform default: WAF rate limit on all of `/w/*` — 10/min per IP. Every namespace gets this automatically. No namespace goes live without a rate limit.

Namespaces can override:

```
/w/*           → default: 10/min per IP (platform)
/w/comment/*   → override: 5/min per IP (declared by comment repo)
/w/admin/*     → override: no limit (declared by admin repo, requires auth)
```

New namespace, no declared limit? Gets the platform default. Safe by default. Opt out explicitly.

---

## Spam defense layers

| Layer | What it does |
|---|---|
| WAF rate limit | Caps requests per IP |
| Edge shape check | Rejects missing token, oversized URLs |
| Build-time token | Proves client loaded the page |
| Processor validation | Token signature, expiry, page exists |
| Moderation | Low-trust comments held for review |
| Logs | Full audit trail, can replay/rebuild |

## Client behavior

Submit:
- POST to `/w/comment/add?...`
- If 2xx → show "comment submitted" (optimistic display for submitter)
- If network error → show "couldn't submit, try again" (form is the retry mechanism)
- No localStorage queue, no service worker, no background sync

Read:
- Fetch `/comments/{pageUuid}/index.json` — one request, all comments
- All responses cached at CloudFront edge

The submitter's client renders the comment optimistically. Everyone else sees it after the processor writes the file and regenerates the index.

---

## Edit and delete

New verbs on `/w/comment/`:

```
POST /w/comment/edit?page={uuid}&requestId={id}&body={newBody}&token=...
POST /w/comment/delete?page={uuid}&requestId={id}&token=...
```

The processor replays events in order. The file on S3 reflects the final state. Delete writes `{"deleted": true}`. The log has the full history.

---

## Recovery

The logs are the source of truth. `/comments/` is a projection — a materialized view.

1. Processor breaks → comments stop appearing, but data is in the logs
2. Nuke `/comments/` → replay all logs → full rebuild
3. Nothing is lost unless CloudFront stops logging (it won't)

---

## MVP scope (one Lambda)

What we build first:

1. **CloudFront Function** on `/w/*` — handles `open` (returns static JWT), shape validation on writes (return 202), rejects garbage (403/413)
2. **One processor Lambda** — triggered by log delivery, validates, writes comment files, regenerates `index.json`
3. **WAF rate limit** on `/w/*` (platform default) + `/w/comment/*` override
4. **Client JS** — calls `open`, gets token, POSTs to submit, fetches `index.json` to read, optimistic display

The client always calls `open`. MVP `open` is just the CloudFront Function returning a static JWT. No Lambda needed for auth yet.

What we don't build yet:
- `open` Lambda (upgrade when you want per-user trust levels)
- Lambda@Edge on read path (upgrade when you want fresher index.json)
- Edit/delete (not needed until there are comments to edit)
- Auth/JWT (separate platform concern)
- Archive/pagination (not needed until a post has many comments)
- Earned trust / reputation (not needed until there's comment history)

---

## Scaling path

The MVP scales already:
- Write path: CloudFront handles millions of POSTs
- Read path: `index.json` is a cached static file
- Processor: no concurrency constraint (request IDs = no coordination)

If latency matters later: plug in Lambda@Edge on the read path (same URL, same client). If spam matters: add `open`. If volume matters: the processor already scales horizontally.
